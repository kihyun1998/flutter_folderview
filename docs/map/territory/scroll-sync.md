# Two-axis scroll sync

## What it is
Scrolls the content vertically and horizontally while keeping the vertical `ListView` fully virtualized. Four controllers are paired so the list and each scrollbar move together, and horizontal scroll is applied per row, not by a scroll view around the list. The bars themselves are [scrollbars](scrollbars.md); how a wheel notch moves the main controllers is [wheel-motion](wheel-motion.md).

## Governing decisions
**None.**

## Design model
Read from `SyncedScrollControllers` and `_FolderViewContentState`.
- **Four controllers**: main vertical, vertical bar, main horizontal and horizontal bar. Each main/bar pair mirrors the other through `_jumpToNoCascade`, which clamps to the follower's extent and sets a one-shot flag (`_doNotReissueJump`) so a mirrored jump does not bounce back. The flag is set only when the jump moves the follower (#178): a `jumpTo` to the offset it already has sends no notification, so the flag stayed and swallowed its next real move. After a bulk expand past the old end, with `wheelMotion: null`, a -120 notch left 98880 / 99000 (body / bar), and with a spring the bar lagged one frame. flutter_table_plus's `NoCascadeGuard.resolveJump` made the same change in its #214. Pinned by the macOS bounce test in `test/widgets/folder_view_scrollbar_wheel_test.dart` (a body overscrolled past the top, with the bar held at 0 by its clamp; without the guard the bar's next `jumpTo` left the body at 0 against 100). The bulk-expand notch tests pinned it before the metrics re-follow (below): that follow now moves the bar after the expand and clears the stale flag in passing, so they pass without the guard (#194).
- **The vertical bar also follows the body's scroll metrics (#194).** The offset listeners mirror only when an offset changes through a call that notifies. Scroll anchoring's correction during a user's scroll (`correctBy`, #195) notifies none and sends no `ScrollUpdateNotification`: the bar follows it on the scroll's next frame through the mirror, and through this re-follow. During a thumb drag the anchor corrects the bar too, since a follow here would end the drag ([scroll-anchoring](scroll-anchoring.md), #203). A body jump made during a build is mirrored clamped to the bar's end of the last layout, and when layout then moves that end no offset changes, so the bar stayed behind (49300 against a body at 50100 after an expand at the end). `SyncedScrollControllers.build` wraps the builder's subtree in a `NotificationListener<ScrollMetricsNotification>`; a vertical notification at depth 0 (the rows' `ListView`, or the vertical bar's own view) calls `_verticalBarFollowsBody`, which moves the bar to the body's offset clamped to the bar's extent. A layout that changes a scroll view's metrics sends one, in a microtask after the frame. The rows' `ListView` lays out on every scroll frame, so it sends one on every frame of a scroll; the bar's own `SingleChildScrollView` only repaints on a scroll, so it sends one only when its own layout changes, and a drag on the bar past its end (bouncing physics) sends none (probed on the macOS target, trackpad, 2026-11-12). The frame in which the extents change is drawn with the bar at its old offset, as it was with the post-frame re-syncs. The follow does nothing when the bar is already there: a `jumpTo` to the offset the bar has ends the bar's activity, a thumb drag or a track tap's animation (removing that early return reddened seven drag and track-tap tests in `test/widgets/folder_view_scrollbar_wheel_test.dart`), and would leave `_doNotReissueJump` set with no notification to clear it. A move sets the flag first, so the bar's listener does not echo a `jumpTo` back to the body. Depth 0 keeps a scroll view inside a row out. The horizontal axis keeps its own re-read on the hidden view (below). Pinned by `test/widgets/folder_view_incremental_anchor_test.dart` and `test/widgets/folder_view_scrollbar_wheel_test.dart`.
- A bar controller takes no wheel itself: upstream's `ScrollbarController` hands wheel input to its main controller and reports the main position's end as its own, and the mirror moves the bar ([wheel-motion](wheel-motion.md)). A thumb drag and a track tap stay on the bar controller and the mirror moves the main one; pressing the bar first ends a motion the main one is running. Moved by `jumpTo`, the main one's `userScrollDirection` stays idle through a thumb drag.
- **Horizontal scroll is per row.** A hidden, zero-height `SingleChildScrollView` holds `horizontalController` so it has a `ScrollPosition`. Its offset feeds a `ValueNotifier` (`_onHorizontalScroll`), from the controller's listener and from the hidden view's `ScrollMetricsNotification` (#179): when new content shrinks the end below the offset, the position is corrected to the new end without notifying listeners, and the rows stayed at the old offset (800 against a bar at 637.5) until the next input. The notification is dispatched after the frame, so the frame of the change is drawn with the old offset and the next one with the new; a same-frame fix would read the offset at paint time. Pinned by `test/widgets/folder_view_scrollbar_wheel_test.dart`. and each row wraps in `OverflowBox` → `ValueListenableBuilder` → `Transform.translate(-offset)` → `SizedBox(contentWidth)` (`_buildItem`). Only visible rows rebuild on a horizontal scroll. When `contentWidth` fits the viewport (`needsHorizontalScroll` false), the wrapper is skipped entirely.
- **The order is a hit-testing requirement (#136).** `RenderTransform` passes a point to its child without checking its own size, so the translate must sit inside the viewport-wide `OverflowBox`: that box tests the untranslated point, and the content-wide `SizedBox` tests the translated one. With the translate outside, everything past the first viewport-width of a scrolled row took no input (CHANGELOG 0.12.0: in a 400 px view scrolled by 300, a tap at x 320 worked and at 500 did nothing). The translate is present at offset 0 too, as an identity, so a row's subtree keeps its State when the offset leaves 0. Pinned by `test/widgets/folder_view_horizontal_hit_test.dart`.
- A row's `RenderBox` is therefore `contentWidth` wide and translated left; its rect extends past the viewport whenever the content is wider than the view ([row-wider-than-viewport](../invariant/row-wider-than-viewport.md)).
- **A View Mode switch replaces all four controllers**, because `SyncedScrollControllers` is keyed by `ValueKey(widget.mode)`, so both offsets start at 0. Intended: the two modes render different row lists (maintainer, 2026-10-25).
- The platform scrollbars are suppressed with `ScrollConfiguration(scrollbars: false)`; the view draws its own ([scrollbars](scrollbars.md)).

## Cross-cutting invariants
- [pre-layout-extent](../invariant/pre-layout-extent.md) — `_jumpToNoCascade` clamps to the follower's extent, which during a build is the old one; the metrics re-follow moves the vertical bar once layout has the new one.
- [row-wider-than-viewport](../invariant/row-wider-than-viewport.md) — the per-row translate is what puts a row's rect off screen.
- [node-id-identity](../invariant/node-id-identity.md) — each row is keyed by its Node's `id`, with a `findChildIndexCallback`.

## Blast radius
- [scroll-anchoring](scroll-anchoring.md) — a programmatic `jumpTo` or `correctBy` on the main vertical controller needs no bar re-sync of its own: the metrics re-follow moves the bar once layout has settled the extents. The exception is a thumb drag: a jump reaching the bar ends it, so the anchor corrects the bar as well. The main horizontal controller has no such re-follow; a horizontal jump made before layout is clamped to the bar's old end.
- [scrollbars](scrollbars.md) — each bar is driven by its paired controller, and the bar's scroll content comes from the same `contentWidth`/`contentHeight`.
- [wheel-motion](wheel-motion.md) — the main controllers are `SmoothScrollController`s, so a mirrored follower receives a `jumpTo` on every frame of a motion. That `jumpTo` ends any motion the follower runs, which is why a motion has one owner.
- [label-tooltip](label-tooltip.md) and [row-card](row-card.md) — they place overlays against row and label rects, which the translate moves.
- [taps](taps.md) — a tap reaches a row only where the `OverflowBox` order lets hit testing reach it.
- [row-geometry](row-geometry.md) — `contentWidth` decides whether horizontal scroll exists at all.
- [scale-input](scale-input.md) — the physics of the `ListView` and of the hidden horizontal view are swapped to block modifier-wheel scrolling.
